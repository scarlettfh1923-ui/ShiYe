如何评价comma.ai创始人George Hotz断言AI编程Agent无法真正编程？

我想起 2016、2017 年实习的时候，公司里有个很厉害的人，我们都叫他明哥。

我不知道他名字里到底有没有这个明字。可在我们那批实习生眼里，他就是项目里最能解决问题的人。谁代码跑不通了，谁问题查不出来了，最后基本都会去找他。

当时我们做的是 C++ 项目。C++ 麻烦的地方不只在语法。内存、生命周期、编译依赖、接口兼容、历史代码，一个小改动就可能牵出一串后果。我们实习生经常改半天，越改越乱。明哥过来看，很多时候也不写多少代码。十几分钟过去，可能只改了几行。

结果还真就把问题解决了。

后来我才慢慢明白，厉害的程序员并不靠打字速度。他知道哪个地方可以动，哪个地方暂时不能动，哪个报错是表象，哪个路径才接近根因。他脑子里装着整个项目，知道一个函数为什么放在这里，一个判断为什么看起来奇怪，一个接口为什么多年没有改。

看到 George Hotz 评价人工智能编程 Agent，我第一反应就想到了明哥。

如果你点进这个问题，除了想看 Hotz 为什么这么说，可能也关心 Agent 到底该怎么学。我见过不少同学的状态，今天收藏提示词，明天装 LangChain，后天看 RAG。看的时候都懂，轮到自己动手，又不知道从哪里下手。

卡住时，某个库的用法通常只占很小一部分。模型怎么接业务，工具怎么封装，输出怎么校验，失败怎么评估，这几件事没有放在同一条工程链路里，学习就会碎。

所以我会建议先用一节系统课把路线顺一遍。我后来正好翻到知乎知学堂这节《大模型应用开发》0 元公开课，感觉它适合放在入门前面看。它讲得比较实在，第一天讲大模型应用、知乎直答原理和 DeepSeek 核心技术，第二天讲知识体系、典型业务场景和岗位分析。你先知道这条路上有哪些模块，再去学框架，心里会稳很多。

顺便提醒两点。课程现在还是 0 元入口，真想学的话可以先领着，后面按自己的节奏看，不吃亏。进群以后遇到概念和项目卡点，也可以问老师，比一个人在教程里来回试要省心。

加老师后还有 Agent 相关资料包，像从零到一笔记、后端面试题、商业项目实战材料。新手可以先照着跑通一遍，再换成自己的小项目重做，效率会高很多。

Hotz 在 2026 年 5 月 24 日那篇文章里说，自己过去六个月试过很多 Agent，也用它们写过 tinygrad 的一部分代码，还用它们做过 USB 到 PCIe 芯片逆向。体验是，一开始进展很快，越到后面越像反复拉老虎机，模型不断给出看似接近答案的补丁，但最后的打磨总差一点。他还提到，未来能做工程的 Agent 需要 world model，也就是对系统状态、约束和后果有持续追踪能力。

这话对刚想学 Agent 的人不太友好。你刚打开几个教程，就看到 Hotz 这种级别的人说 Agent 不会编程，很容易一下子泄气。

但我觉得可以换个角度看。如果 Agent 自己都容易卡在上下文、工具调用、测试验证这些地方，那人学 Agent 时也不能只盯着某个框架。

Hotz 的判断刺耳，但点到了现在编程 Agent 的短板。

一个常见的编程 Agent，大致会做几件事。先从代码库里检索相关文件，再根据需求生成计划，然后修改文件、运行测试、根据报错继续修。看起来已经很像一个初级程序员在工作。

这张图也能当学习顺序看。如果你现在也处在学完一点工具，却做不出完整项目的阶段，可以先把模型调用和业务接入过一遍，再找一个小需求，照着上下文检索、工具调用、测试验证、日志修复跑一圈。

里面如果有项目拆解和资源包，可以先跟着跑一遍。跑通以后，再换成自己的小项目重做一次。它不能替你完成项目，但能让你少在开头绕路。很多人已经很努力，只是一直在零散教程之间跳来跳去。

麻烦也出在这里。

Agent 读到的是文本片段，工程师要理解的是运行中的系统。代码库里很多约束不会写成注释。某个字段不能随便改，因为老客户端还在用。某个判断看起来多余，因为它服务于一批历史数据。某个函数返回值很别扭，因为下游三个模块都默认了这种格式。

这些东西很少完整出现在上下文窗口里。

所以 Agent 经常能找到相关文件，却找不全相关约束。它能解释一个函数，却未必知道这个函数在线上到底兜着哪些情况。它能让测试变绿，却可能绕过了测试没有覆盖的行为路径。

这也是人工智能写代码容易让人误判的地方。

以前一段代码写得差，往往一眼能看出来。变量乱，结构乱，语法也可能错。现在模型生成的代码格式整齐，命名像样，注释也体面。它可能通过一部分测试，还可能把实现写得很完整。麻烦藏在抽象边界、状态同步、错误处理、权限校验、并发时序、性能退化和兼容性里。

这些地方才是长期维护里最花钱的部分。

Hotz 的批评可以放到工程流程里理解。Agent 适合从空白页生成第一版，也适合写脚手架、补样例、查 API、整理日志、生成测试草稿。它在边界清晰的小任务里很有用。可一旦任务变成在复杂系统里做低风险修改，它就需要外部约束来兜住自己。

这些约束包括强类型、单元测试、集成测试、清晰模块边界、代码审查、运行日志、回滚方案。约束越强，Agent 犯错越容易被发现。约束越弱，Agent 越容易把看起来能跑的代码塞进系统里。

如果用 Agent 学编程，学习方式也要换。

很多人上来就问，帮我写一个功能。这样当然能得到代码，但学到的东西有限。更好的用法，是让 Agent 帮自己拆解工程师的思考过程。

可以让它先做代码阅读。

请阅读相关文件，给出调用链、输入输出、状态变化和可能的不变量，改代码放到下一步。

练的是系统阅读能力。看代码时不要只看函数做了什么，还要看它被谁调用、返回值流向哪里、异常怎么处理、状态在哪里保存。

然后让它先写失败测试。

请先写一个会失败的测试，说明这个测试覆盖哪条行为路径，以及它为什么能证明问题存在。

这样会逼自己区分现象和可验证行为。很多 bug 之所以越修越乱，是因为人还没说清楚要证明什么，就开始改实现。

接着再让它给最小补丁。

请给出最小补丁，列出每个修改点对应的原因，保持现有接口和数据结构稳定，除非能说明哪些调用方会受到影响。

练的就是改动范围控制。工程里很多危险来自过度修改。一个只需要改边界条件的问题，被改成了重写模块，风险会立刻扩大。

改完以后，让它做代码审查。

请用 code review 的方式检查这次改动，关注不变量、边界条件、并发、性能、权限、兼容性和测试盲区。

这里可以把 Agent 放到质检位置。它不一定能发现所有问题，但它会提醒你从哪些维度看代码。久而久之，人会形成自己的审查清单。

测试失败时，也不要让它立刻继续补丁。

请先解释失败日志对应的执行路径，再提出修改方案。

这个习惯很有用。因为很多 Agent 的坏习惯，是看到报错就修报错。类型错了就改类型，字段缺了就补字段，空指针就加判空。可学习编程时，更应该追问为什么这个值会走到这里，为什么这个状态被破坏，为什么之前没有出问题。

这样用下来，人仍然负责理解和判断，Agent 负责加速阅读、生成候选方案和补充检查角度。

所以我不认为 Hotz 的话应该被理解成人工智能写不出代码。它当然能写，很多时候写得还不错。可工程意义上的编程，要求一个人持续维护系统约束，知道改动会影响谁，知道哪些测试能证明行为，知道哪些代码看起来奇怪但不能乱动。

这部分能力，今天的 Agent 还不稳定。

对学习者来说，人工智能编程 Agent 更适合放在阅读助手、测试助手、审查助手和调试陪练的位置。每次让它写代码之前，先让它解释系统。每次接受补丁之前，先让它说明风险。每次测试通过以后，继续问还有哪些路径没有覆盖。

我建议你跟着【Agent从入门到实战】仔细的过一遍，你自己亲自做过一遍，印象也更深刻，你看别人代码看懂和自己写出来是完全不一样的概念。
